# Catalog migrations

Migration 0001 creates Catalog-owned titles, immutable rights revisions and actor/time/correlation provenance. Migration 0002 adds optional metadata for existing drafts, immutable command/metadata audit, trusted publication attestations, receipts and publication outbox. No existing metadata is invented or backfilled.

Migration 0003 adds a non-materialized, security-barrier public_candidates view joining the current title, latest approved rights and exact publication. The partial published-title ID index supports keyset/detail reads. The NOLOGIN aster_catalog_reader group has only schema USAGE and view SELECT: no writes, direct history/audit access or Identity privileges. The view is internal to the Catalog service and contains facts needed for domain validation, not the DTO returned to clients. Application SQL checks current expiry/permissions before LIMIT; one statement joins a consistent snapshot. [PostgreSQL view privileges](https://www.postgresql.org/docs/18/sql-createview.html) explain why the view uses owner privileges rather than security_invoker.

The runtime role can update title lifecycle/metadata and insert history, audit, receipts and outbox. It cannot change/delete history, audit or outbox, write technical attestations, create schema objects or read Identity data. Only expired receipts are deleted by the owning application. The separate local initializer uses administrator credentials; the operator CLI requires the restricted aster_catalog_local login and probes privileges before use.

Rights append advances version/latest revision and writes facts/provenance atomically. Workflow commands use one title lock and one transaction; the metadata/lifecycle update accounts for that single version increment. Owner foreign keys prevent substituting another title/review's publication. Audit retains metadata/artwork rights snapshots. Receipts and outbox refer to the corresponding title-version audit.

Unique bounded slot columns enforce at most 64 receipts and 128 pending events/title even if callers race. The application reserves each final slot for takedown. No broker relay or background cleanup is implemented here.

Source rights/metadata JSON is limited to 30000 UTF-8 bytes, stored JSONB to 32768. Parameters are split without breaking surrogate pairs to preserve the shared adapter's 4096-character limit. Rights history reads use descending keysets up to 50 entries.

The initializer takes an advisory lock, validates contiguous versions, applies forward migrations once and refuses unknown schemas/unsafe local roles. Each migration has a one-second lock timeout and two-second statement timeout. Duplicate raw installation fails; the initializer is idempotent. Phase 06 applied additive 0004/0005 to the retained development database through this initializer; editorial data was not rewritten.

Migration 0004 adds Catalog-owned media_requests with title/revision foreign keys, immutable actor/time/correlation audit, globally unique request IDs and a per-title source/recipe fingerprint. Sixteen unique bounded slots/title prevent unlimited admission. Requests have a 4096-byte input JSON bound and 8192-byte stored JSONB bound. The runtime has SELECT/INSERT only; public readers have no access. Admission does not change editorial versions or publication pointers. No backfill is required and earlier binaries can ignore the added table.

Down 0004 takes an exclusive lock and refuses any retained request before attempting DROP without CASCADE. Its empty-table down/up is verified; after admission, retain audit and roll forward. Do not delete requests to make a rollback succeed. Request tests use a new labelled tmpfs fixture. [Phase 06 request evidence](../../../evidence/phase-06/media-requests.md).

Migration 0005 adds private acquisition attempts: three/request, one global RUNNING row, immutable identity fields in the validated record and conditional RUNNING-to-terminal updates. Runtime may SELECT/INSERT/UPDATE but not DELETE/TRUNCATE; public readers have no access. Attempts never grant attestation writes. Its down migration refuses retained audit; empty-only 0005 then 0004 rollback/reinstall and recovery are tested. Keep the current initializer after upgrade: older initializers reject unknown schema versions even though the additive tables do not break old HTTP readers. [Actual acquisition/migration evidence](../../../evidence/phase-06/acquisition.md).

Migration 0006 adds private processing attempts: three/checksum-recipe, one global RUNNING row, a 4096-byte record bound and conditional terminal updates. It references retained acquisition/request identities and grants no publication access. The initializer applies 6 without backfill; old initializers reject it. Empty-only down/up and nonempty refusal are tested. After processing, retain audit and roll forward; no rights, metadata or publication migration is needed. [Processing evidence](../../../evidence/phase-06/processing.md).

Rollback scripts are destructive and only for explicitly disposable fixtures: down 0002, then down 0001. They omit CASCADE; unexpected dependencies prevent removal. Down 0002 discards new metadata/audit/receipts/outbox and removes attestation ownership constraints; it is not a production rollback. After actual publication, use backups and roll-forward, or retire through the owning command. Never delete rights/audit or pending events to recover capacity.

When 0003 is installed, remove it before 0002 and 0001. Down 0003 removes only its view/index/reader group and preserves product/audit rows. Unexpected dependent objects prevent removal. Index creation is bounded by the same lock/statement deadlines; these small local fixtures do not prove an online large-table migration. The new metadata decoder reads both legacy five-field and current ten-field snapshots; new writes use ten fields. Keep that decoder when rolling back public transport after new writes: an older binary cannot read the expanded snapshots. No backfill or immutable-history rewrite is required.

The [operator guide](../README.md) documents startup and commands. [Integration evidence](../../../evidence/phase-03/README.md) covers fresh installation, down/up, role isolation and transaction behavior on local PostgreSQL, not an online production migration.
