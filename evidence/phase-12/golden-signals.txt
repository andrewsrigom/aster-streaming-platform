## Implemented sources

| Operational question | Signal |
| --- | --- |
| Are requests slow, failing or saturated? | existing HTTP duration, outcomes and active requests |
| Is a dependency slow, failing or saturated? | existing dependency duration, outcomes and active operations |
| Is Node runtime pressure rising? | process CPU time/utilization, RSS, uptime, official event-loop/V8/runtime instruments, plus heap used/total, external and array-buffer bytes |
| Is a PostgreSQL pool saturated? | latest maximum, total, idle, reserved and vendor-waiting counts by finite pool role and lifecycle state |
| Are events delayed or failing? | publish/consume outcome and validated age for Identity, Catalog and Engagement owners |
| Is media-worker work active? | existing `media_worker/process` dependency-active instrument around the isolated coordinator |

The implementation does not invent a worker queue that the current one-at-a-time
coordinator does not own. Future, invalid or older-than-seven-day event times
retain their finite delivery outcome but emit no fabricated age; product
duration is bounded at 300 seconds. PostgreSQL snapshots are recorded at creation, acquisition/
release and close transitions; observation failure cannot change connection or
transaction behavior.

## Interpretation and limits

These signals answer availability, latency and saturation questions for current
Node processes, dependencies, pools, event delivery and the media coordinator.
They are diagnostic only: PostgreSQL remains authoritative, metrics do not
change acknowledgement or retries, and no shared-host result is a capacity or
SLO claim. Broker in-flight state remains represented by dependency-active and
delivery outcomes; a separate arbitrary queue label was deliberately not added.
