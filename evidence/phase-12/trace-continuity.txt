# P12-R01/R02 trace continuity

Exact source: 03abe8ac6d30c34902442367da241e0c295ff122

Verified representative paths

1. Inbound HTTP
   - a real Express/Apollo Identity request accepts one validated W3C parent;
   - `aster.http.server` continues that trace with a new server span;
   - an asynchronous dependency span is its child;
   - a structured log emitted inside the child carries that exact trace/span;
   - query text and sensitive request values are absent.

2. Synchronous owner reads
   - Engagement runs under its active server span;
   - the Identity owner client starts a child `identity/read` dependency span;
   - the injected header carries the child span, not the server span;
   - collected client/server spans share a trace and explicit parent relation.
   - Playback and Discovery use the same child-context injection path for their
     fixed Catalog reads.

3. Asynchronous events
   - Identity preserves its active real request `traceparent`, or a bounded
     fallback only when invoked without a telemetry composition, in its signed
     v1 fact;
   - Engagement authenticates and validates the event before observation;
   - broker consumption starts a new local trace with one link to the producer,
     rather than keeping the producer request span open;
   - durable consumer work and its structured log execute inside that linked
     observation, so nested database spans and log context share the consumer
     trace;
   - logs do not include event, account or profile identifiers.
   - Catalog events accept the same optional validated producer context;
   - the real local Catalog operator creates a finite `aster.event.produce`
     span and persists its active context with publication/retirement facts;
   - this transaction does not emit a false broker dependency metric; the
     actual outbox relay owns the later Kafka publish dependency;
   - Discovery scopes owner reads, projection persistence, checkpointing and
     its structured log inside the linked consumer observation.

4. Media and infrastructure
   - the Catalog processing coordinator creates one finite
     `media_worker/process` boundary around handoff, retention and completion;
   - success, replay and failure map to stable span outcomes;
   - the isolated decoder still receives no network, credentials or arbitrary
     inherited telemetry configuration;
   - the actual base-plus-media candidate path supplies the one-shot
     coordinator only the validated local OTLP endpoint and performs one
     bounded final flush before telemetry shutdown;
   - existing PostgreSQL, Redis, broker and object-storage observations become
     children whenever invoked in an active trace scope.

All five subgraph HTTP compositions now run the actual request handler in the
server trace scope and supply active context to their default logger. All five
accept the same validated optional OTLP metrics endpoint, from which the fixed
`/v1/traces` endpoint is derived.

Limitations

- This is representative contract coverage, not a claim that every GraphQL
  field emits a distinct span.
- Protected run `33300561121`, clean blocker-focused confirmation, PR45 squash
  main `ce66f9c` and exact-main run `33301425220` verify the latest media-path
  and real Catalog-producer corrections.
- No high-cardinality request, user, profile, title, URL or GraphQL document is
  added to a span.
