## Outcome

Persist structured rights revisions and actor/time/correlation provenance in Catalog-owned PostgreSQL. Prove atomic history and concurrency with real PostgreSQL. This is a persistence slice, not operator authentication, public browse or a running API.

## Current behavior

P03-R01 is committed as 4968d42 on feat/p03-catalog-rights: 52 domain tests and 52 source tasks pass. Phase 02 main ec6386c and its protected/post-merge Docker proof remain unchanged. Catalog has no durable data yet.

## Proposed behavior

Add the first Catalog migration, application-facing transaction port and PostgreSQL adapter. Each immutable rights snapshot has an increasing per-title revision and audit provenance. A transaction serializes against its title, advances its version and inserts rights/audit atomically. Reads use bounded revision keysets. Reuse the existing PostgreSQL adapter and pg version; no ORM, runtime or new external version.

## Boundaries

- Owner/data: Catalog schema, titles, rights history and review provenance.
- Paths: services/catalog application/persistence/migrations/tests, tools/run-catalog-integration.mjs and workspace wiring.
- Decisions: ADR-0002, 0003, 0004, 0006, 0007, 0010, 0013, 0014.
- Skills: agent, architecture, node-runtime, data-events, security, testing, documentation.
- Trust: storage does not authenticate actors or approve licenses; the future owning application must do so. No transport exposes these methods. Viewer credentials remain unrelated.
- Dependency: PostgreSQL 18.6 through the bounded adapter. A disposable labelled loopback-only integration container must not touch the Aster demo.

## Invariants

- Every stored rights revision is domain-normalized, bounded and matches its relational identity/revision/status.
- Runtime credentials cannot update/delete rights history or provenance.
- Append requires the current title version and next revision; stale writers fail without partial rows.
- SQL locks cover database operations only; no media or external review calls.
- Catalog credentials cannot read other contexts or perform DDL.
- History pages use descending immutable revision keys, maximum 50.
- Stored APPROVED status is not proof of authorization: the next operator slice must invoke approval policy and authenticate the reviewer.

## Failure behavior

| Failure | Expected behavior | Telemetry |
|---|---|---|
| Invalid input/corrupt row | Reject or roll back | Bounded dependency outcome |
| Stale title/revision | Conflict, no writes | Returned result |
| Cancel/timeout/database outage | Abort or indeterminate, never false success | PostgreSQL telemetry |
| Post-write failure/missing title | No orphan history/audit | Rollback |
| Migration/rollback dependency failure | Transaction fails intact | Integration artifact |

## Data and contracts

Migration 0001 adds Catalog-owned tables and restricted privileges, forward/down SQL and no backfill. Rights use a bounded structured JSONB snapshot plus relational identity/revision/status and foreign keys. Immutable audit binds actor/time/correlation to each revision. No broker/outbox yet: publication/retirement events belong to the later lifecycle application slice. No cache/GraphQL/browser change. Rights/audit are durable product evidence, not time-evicted logs; paginate and never silently prune them.

## Security and privacy
