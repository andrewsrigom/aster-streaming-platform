QUESTION AND SCOPE
------------------

Question: Can an operator deliberately remove the complete current Aster local Compose project and its durable PostgreSQL volume through one Docker-only command while unsafe inputs fail closed and unrelated Docker resources and images remain unchanged?

Implemented scope:
- one executable POSIX shell command with no Node.js or pnpm runtime dependency;
- exact `ASTER_ENVIRONMENT=local` marker and `DELETE-ASTER-LOCAL-DATA` confirmation;
- fixed Compose project `aster` and repository file `infra/compose/compose.yml`;
- hosted CI, connection URL, Docker endpoint override, remote endpoint scheme, extra argument, symlink, service-set, resource-count, and label refusal;
- explicit validation of Compose project, service, file, network, volume, environment, scope, authority, and owner labels;
- scoped `docker compose down --volumes` with no image or broad prune operation;
- zero-resource postconditions and empty-state idempotence.

Explicitly absent:
- hosted database, Redis, Docker daemon, credential, or infrastructure mutation;
- arbitrary target, project, Compose file, URL, path, or passthrough option;
- global container, network, volume, image, or system cleanup;
- database backup, migration, seed, or product schema;
- application service or endpoint.

OFFICIAL COMMAND BEHAVIOR REVIEW
--------------------------------

Primary sources reviewed:
- Compose project-name precedence: https://docs.docker.com/compose/how-tos/project-name/
- Compose `down` behavior: https://docs.docker.com/reference/cli/docker/compose/down/
- Compose named-volume labels: https://docs.docker.com/reference/compose-file/volumes/
- Docker object-label inspection: https://docs.docker.com/engine/manage-resources/labels/

The Docker documentation states that the CLI project-name option has the highest precedence. It also states that `down --volumes` removes named volumes declared by the Compose file, while external volumes are never removed. Compose automatically records project and logical-volume labels. The reset therefore pins the CLI project name and Compose file, rejects a model outside the reviewed service and volume set, verifies existing resource labels, and uses the supported Compose teardown instead of manually enumerating broad removals.

SECURITY, FAILURE, AND RECOVERY INTERPRETATION
----------------------------------------------

- The operator is the actor; local durable PostgreSQL data and unrelated Docker resources are the protected assets.
- Arguments, environment, Docker context metadata, repository paths, Compose model, and Docker labels are untrusted boundaries.
- The command prints no connection URL, credential, Docker certificate path, database content, or secret environment value.
- Every refusal and metadata failure occurs before the scoped teardown.
- A teardown or postcondition failure exits nonzero and deliberately avoids global fallback cleanup.
- The command retains images and build cache. Recovery from an intentional reset is a new empty startup; migrations, seeds, and backup restore remain owned by later work.
- No GraphQL, browser, accessibility, product-data, event, cache-key, or application-runtime behavior changes in this work item.

LIMITATIONS
-----------

- Runtime evidence covers Docker Desktop through WSL on linux/amd64. Native Windows, macOS, rootless Docker, Podman, alternate Compose implementations, and arm64 runtime behavior remain unverified.
- A local Unix socket or Windows named pipe proves the ordinary client endpoint is local; it cannot prove that a deliberately installed local proxy does not forward elsewhere.
- The fixed service and volume allowlists match the current P01-R01 slice. Later Phase 01 dependencies must update the reset contract and adverse tests before their data becomes resettable.
- The command intentionally rejects Docker configuration overrides, CI environments, and exported database or Redis URL variables even when an operator believes they are local; the safe recovery is to unset them and re-run against the inspected local context.
- Deleted local PostgreSQL data is irreversible because backup, migration, and seed recovery are not implemented yet.
